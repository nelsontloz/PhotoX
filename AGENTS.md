# PhotoX — Agent Notes

Personal photo/video hosting: one NestJS `core` API (the only public/business API; external exposure goes through a reverse proxy that is not in this repo) + one BullMQ `worker-service` (a second, internal Nest HTTP app: `:3004`, `GET /health` only) + Vite `web`, plus a Flutter `apps/mobile` backup client kept outside the pnpm workspace, sharing Redis, local-disk media (`STORAGE_DIR`), and an S3-compatible object store used only for per-user backups (Floci in dev). Single Postgres DB (`photox`) owned exclusively by `core` — old docs claiming MinIO or multiple DBs are stale.

## Layout

- `apps/core/` (`@photox/core`, :3000, no published port in compose) — the sole public API app: auth, assets, files, upload sessions, albums, shares, faces/persons, search, backups, trash, admin. There is no places route group: `apps/core/src/places/` holds only `PlacesResolveService`, and place data lives on asset columns filled during metadata writes and via admin `POST api/v1/admin/places/backfill`.
- `apps/worker-service/` (`@photox/worker-service`, internal: Nest HTTP on `WORKER_SERVICE_PORT`/3004 exposing just `GET /health`, 503 when Redis is down) — 8 BullMQ consumers; no DB access: reads/writes go through core HTTP via `CoreClient`, media bytes go directly to `STORAGE_DIR`
- `apps/web/` (`@photox/web`, :5173) — Vite + React, talks to core same-origin via `/api` (a `/worker` proxy exists for e2e; browsers never call it)
- `apps/mobile/` — Flutter (iOS + Android) backup client for the device camera roll, talking to core's HTTP API directly with Bearer JWTs. **Not** a pnpm workspace package (it has no `package.json`): Turbo, `pnpm build`/`verify` and Jenkins deliberately never see it, because it needs Flutter 3.47 + the Android SDK and `flutter build ios` only runs on macOS. Build and gate it with `pnpm mobile:*`.
- `apps/core/src/database/` — TypeORM entities + core-only `DatabaseModule` + migrations
- `apps/core/src/uploads/` — resumable chunked sessions (`api/v1/uploads`) + the advisory-locked 15-min sweeper
- `packages/shared-config/` — zod `loadEnv()`/`loadAuthEnv()`/`loadRootEnvFile()`, `LocalStorageService`, backup-path helpers; `packages/shared-types/` — wire interfaces, `JwtPayload`, embedding constants (`FACE_EMBEDDING_DIM` 512, `SEARCH_EMBEDDING_DIM` 768, `SEARCH_EMBEDDING_MODEL` `siglip2-b16-224`)
- `docker-compose.yml` is infra-only: `postgres` (pgvector image, single `photox` DB) + `redis` + `floci` (S3-compatible backup store, `:4566`, no healthcheck); `pnpm dev` runs the apps on the host. `docker-compose.e2e.yml` merges over it via `e2e/run.sh`: adds `core`/`worker-service`/`web` containers, only `web` publishes a port (`E2E_WEB_PORT`, random per run), worker mounts host `./data/storage/models` read-only (models must be on the host). `docker-compose.mobile-e2e.yml` merges over both for `pnpm mobile:e2e`: it publishes core on host loopback (`MOBILE_E2E_CORE_PORT`, default 3000) and drops the web port, since the Android AVD reaches core through `adb reverse`.

## Commands

```bash
docker compose up -d postgres redis floci   # infra FIRST (floci only needed for backups)
pnpm dev                                    # turbo persistent: core + worker + web on the host
pnpm --filter @photox/core dev              # single package (@photox/core | @photox/worker-service | @photox/web)
pnpm verify                                 # lint && test --force && typecheck && build && E2E_BUILD=1 test:e2e
curl localhost:3000/health                  # core (host dev); compose publishes no core port; worker health on :3004
pnpm mobile:verify                          # flutter analyze && flutter test && build_runner --only-check (apps/mobile)
pnpm mobile:build                           # flutter build apk --release (apps/mobile; iOS needs Xcode)
pnpm mobile:e2e                             # opt-in on-device e2e: compose stack + Android AVD (e2e/mobile/run.sh)
```

Node 24 (`.nvmrc`), pnpm 9.15.0 (`packageManager`). After pulling: `pnpm install` (root `postinstall` downloads all 3 worker models unless `FACE_MODEL_SKIP=1`), diff `.env` against `.env.example` for new required keys, start compose, then `pnpm dev`.

## Env / config

- `packages/shared-config/src/env.ts` (`loadEnv`, zod): `API_PORT` 3000; `CORE_URL` (worker→core, default `http://localhost:3000`, compose `http://core:3000`); `POSTGRES_*` (core only); `REDIS_*` (localhost defaults; `REDIS_PASSWORD` optional — testcontainers Redis is passwordless, compose defaults `photox_dev` and runs `--requirepass`; `REDIS_DB` logical index, `0` in production, set per spec file by the integration harness); `STORAGE_DIR` (default `./data/storage`, anchored at workspace root — core and worker have different cwds); `STORAGE_QUOTA_BYTES` (optional; over-quota originals 413 before the original is stored, checked after the dedup fast-path, though multipart temp bytes / session chunks may already be on disk); `S3_*`/`AWS_*` (backups; dev defaults target Floci); `AUTH_ACCESS_TTL` 30m; `AUTH_REFRESH_TTL` 1d (sliding idle window; parsed to **ms** in the schema while `AUTH_ACCESS_TTL` stays a string); `AUTH_CLOCK_TOLERANCE_SEC` 60.
- `loadAuthEnv` (same file): `AUTH_TOKEN_SECRET` + `WORKER_JWT_SECRET` required, each ≥32 chars **and** entropy-checked (≥16 unique chars, no 6-char run); worker secret must differ from the auth secret. `AUTH_TOKEN_SECRET_PREVIOUS` is optional rotation overlap (never signs).
- No `@nestjs/config`: each `app.module.ts` calls `loadRootEnvFile()` (Node `process.loadEnvFile`, root then cwd `.env`; existing process env wins). Direct `process.env` reads instead of zod: `WORKER_SERVICE_PORT`, `ADMIN_EMAIL`/`ADMIN_PASSWORD`, `FACE_DETECTOR_MODEL_PATH`/`FACE_MODEL_PATH` (detector path via `resolveFaceDetectorModelPath()`, default `STORAGE_DIR/models/det_10g.onnx`), `FFMPEG_PATH`/`FFPROBE_PATH`, `RATE_LIMIT_REGISTER`, `NODE_ENV`, `S3_ENDPOINT`.
- Turbo 2 strict env: only keys in `turbo.json` `globalPassThroughEnv` reach tasks — add new test/script env there (e.g. the `TESTCONTAINERS_*` vars).

## API conventions

- Controllers declare `api/v1/...`; no global prefix. Core health is unversioned (`health`) and returns 200 even when degraded; the worker's own `/health` (`:3004`, unpublished) returns 503 when Redis is down. Public share is `api/share/*` (token + asset/album children).
- Uploads have two front doors, one ingest core: legacy multipart `POST api/v1/files` (still what the web client uses) and resumable sessions under `api/v1/uploads` — `POST /`, `GET /:uploadId`, `PUT /:uploadId/parts/:index`, `POST /:uploadId/complete`, `DELETE /:uploadId`. Sessions use 8 MiB chunks, 4 GiB max, ≤5 active, a 24h pending TTL (6h for an assembled retry), machine-readable error codes, and a 15-min advisory-locked sweeper; chunks land under `STORAGE_DIR/upload-sessions/<userId>/<sessionId>/part-<n>`, and both doors converge on `persistOriginal -> createAsset -> enqueueAssetJobs`. Both answer the same ingest contract: the sha256 checksum is the natural key, so a **duplicate is success** — `201` when that request stored new bytes, `200` + the existing asset when it did not (never a 409), with an `IngestErrorCode` machine code on every error; `GET api/v1/files/quota` reports the limit the 413 would enforce.
- `apps/core/src/main.ts` (mandatory, keep in sync): `ValidationPipe({whitelist, forbidNonWhitelisted, transform})` + `HttpExceptionFilter` + Swagger `/docs`/`/docs-json` + static security headers; `trust proxy` 1 is load-bearing for per-IP rate limits; no CORS (browsers reach core same-origin through the Vite dev proxy or a reverse proxy). Worker `main.ts` is intentionally bare.
- DTOs live next to controllers with class-validator; wire interfaces live in `shared-types`.
- Albums carry `hiddenFromTimeline` (default false): assets in a flagged album are excluded from the timeline query and the layout, but not from album-scoped reads (`GET api/v1/assets?albumId=`, `GET api/v1/albums/:id/assets`), the trash view, id-batch reads (`?ids=`, the worker's fetch) or search/persons/shares. `version` must still fold hidden-album membership in, because album changes never bump `assets.updatedAt`.
- Timeline sync is two routes: `GET api/v1/timeline/index?tz=<IANA>` returns local-calendar-month windows `{key,from,to,count,version}` and is the revalidation call, and `GET api/v1/timeline/window?from&to&offset&limit` returns one window page (`version`, `total`, `items`, `nextOffset`) — the client passes the index's instants back verbatim, and `offset` there is a row index inside that window, not the collection's cursor. `version` is opaque (compare for equality only) and covers asset mutations plus hidden-album and (for `albumId=`) album-membership touches, never person clustering (`faces` has no `updatedAt`); the normative copy is `AssetLayoutMonth`/`AssetLayoutPage` in `shared-types`. Each route has its own DTO, so a param from the other family is a 400. `from`/`to` are required (a bare window read is a 400); neither response carries an ETag, because the client must always read the version.
- Trash is a state of the asset, not a namespace: `GET api/v1/assets?isTrashed=true` is the trash view, `POST`/`DELETE api/v1/assets/:id/trash` trashes/restores, `DELETE api/v1/assets/:id` purges (400 unless trashed, 404 once gone) and `DELETE api/v1/assets?isTrashed=true` empties the trash (204; 400 without that explicit filter, so a client that drops its query string cannot delete a library).

## Auth

- `argon2` only (never bcrypt). Access = HS256 JWT; refresh = opaque token, sha256-hashed at rest, rotated per use with reuse detection (a reused token revokes **its own device session**, not the user's other devices). Idle window 1d, hard **7d absolute cap**. Sessions are per device: `refresh_tokens.sessionId` is minted per login/register and kept across rotations, the access token carries it as `sid`, and the guard 401s once that session's rows are gone — so logout (by refresh token, or by the presented access token's `sid` when none is sent) kills one device and leaves the rest signed in. Admin edits and account wipes are the exception: they bump `users.tokensValidAfter`, a user-wide floor the guard enforces on every token. Logout's access-token path is verified with the user secrets only, so a worker `act` token fails closed and revokes nothing.
- `JwtPayload` = `{ sub, email, role, iat, exp, jti?, sst?, sid?, act? }`. The guard tries **auth secret → `AUTH_TOKEN_SECRET_PREVIOUS` → worker secret** (Bearer wins over cookie), sets `req.user`, and ignores incoming identity headers. A token without a non-empty `sub` never authenticates: that explicit 401 is load-bearing — under TypeORM 0.3 the subject lookup degraded to "the first user row" (it dropped undefined `where` values) and the ownership filter lost its tenant predicate; TypeORM 1.x throws on undefined `where` values instead, so both layers fail closed. `photox_access` HttpOnly cookie (SameSite=Lax, Path=/api, re-minted past half its TTL); the refresh cookie is scoped to `/api/v1/auth`.
- Worker-minted tokens (`act`, signed only with `WORKER_JWT_SECRET`, always `role: 'user'`) are default-denied everywhere except the `/worker/*` job surface — no admin reach — plus one route-scoped list read outside it: `GET /api/v1/assets?ids=` (the worker ranking fetch). That exception is keyed on the route + a non-empty `ids`, never on the query shape alone (keying it on `?ids=` made every such route service-token reachable, including the byte-serving file stream). Open routes are exactly `/docs*`, `/health`, `api/v1/auth*`, `api/share*` (file streams are authenticated). `api/v1/admin*` gets the admin role check centrally. The path rules live in `apps/core/src/auth/open-routes.ts` and are matched with a case-insensitive RegExp — the same semantics the router uses — because the router matches routes case-insensitively: the casing of a URL must never decide the policy (a case-sensitive prefix check let a non-admin reach the admin surface via `/API/V1/ADMIN/...`).
- Job binding: core stamps `sig = HMAC(WORKER_JWT_SECRET, userId:scope)` into each payload at enqueue (scope = first present of assetId/fileId/userId); the worker threads it back as `X-Job-Signature` and the guard recomputes/403s — fail-closed, so replay is confined to the scope (the asset for media jobs, the user for cluster/user-scoped jobs), never the jobId. Worker-origin tokens without `act` are 401.
- Rate limits are Redis-backed and **fail closed (503)** on Redis errors (300ms budget): login 5/15m per ip+email plus a coarser 20/15m per-IP bucket (email rotation can't multiply the allowance), register `RATE_LIMIT_REGISTER` (default 10/h), refresh 30/15m.
- Admins: registration always mints `user`. Seed via `ADMIN_EMAIL`+`ADMIN_PASSWORD` (only when no admin exists) or `pnpm --filter @photox/core admin:create [--email= --password=]` (unconditional).
- Sign-ups are governed by the `registration.enabled` `app_settings` row (raw jsonb boolean; a missing row or a non-boolean means on, so no migration or seeding). When it is off, `register` 403s before consuming its rate-limit slot, `GET api/v1/auth/registration` (open) reports `{ enabled }`, and admin `POST api/v1/admin/users` still creates accounts (role defaults to `user`). Every sign-up/create path refuses an address that collides **case-insensitively** with an existing account (open sign-up stores the email raw, admin paths normalize it — the `LOWER(email)` checks keep one normalized identity per account, at the cost of a sequential scan until a functional index exists).

## Jobs (BullMQ over Redis)

- Publisher: `apps/core/src/queue/bullmq.service.ts`. Worker consumes 8 queues: `process-thumbnail`, `process-video`, `process-metadata`, `process-faces`, `process-faces-cluster`, `process-embeddings`, `process-detect`, and `user-delete` (all eight start from one explicit loop in `ProcessorsService`, which awaits the Redis connection first and try/catches each registration so one bad queue cannot abort the rest). Core consumes exactly two queues of its own, `backup-transfer` and `restore-transfer` (backup/restore transfers run in core, never in the worker); every other queue it only produces (`user-delete` included) and reads job state for the admin delete-status poll. The account wipe is batched: the worker's `user-delete` consumer drains that user's pending media jobs, then loops `POST /worker/users/:id/purge/step` (job-bound, target = the job's own user, one short transaction per call: `tokens` → `assets` ≤200/row-batch → `files` → `faces` → `persons` → `albums` → `shares` → `sessions` → `ledger` → `user` last) until `done`, sweeps the four storage prefixes itself via `sweepUserStorage` (shared-config; the worker owns `STORAGE_DIR`, core does not touch bytes), and reports `POST .../purge/finish` with `filesDeleted`/`filesFailed`. The run is `wiping-files` once the rows are gone (the worker is sweeping), then `completed`, `partial` (rows gone, some bytes left — a retry can fix it) or `failed`, recorded in the durable `user_deletes` row that also backs the admin status poll. Sessions are killed on the first step, so the account is locked while the batches drain; a restore/merge for that id answers 409 until the wipe is terminal. Orphan cleanup is inline-only (`POST api/v1/admin/cleanup-orphans/run`; there is no queue or consumer for it). There is no `cleanup-asset` queue: permanently deleting a trashed asset removes its rows only, so the bytes stay on disk until an orphan sweep runs.
- Defaults: `attempts: 3`, exponential backoff, `removeOnFail: true`; video overrides `attempts: 2` (a retry can cost ~1h of SVT-AV1) and `user-delete` overrides `attempts: 5` + `removeOnFail: false` (a batched wipe can fail minutes in; the failed record stays inspectable). jobIds are the dedup contract (`thumb*`/`video*` per asset+size, `embed-`/`detect-` per asset, `face-reembed-`, cluster per user per click, `user-delete-<userId>`); restore re-enqueues are run-tagged because a retained completed jobId silently swallows later runs.
- Backups/restores are a durable per-file ledger in core, executed by two core-owned BullMQ queues (`backup-transfer`, `restore-transfer`; one job per item, jobId `<kind>-<itemId>`): `backup_runs` + `backup_run_items` (successful items are deleted; `queued` means handed to a queue; at most one active run per user, enforced by the partial unique index `UQ_backup_runs_active_user` — two starts that race the `assertNoActiveRun` read would share one S3 prefix and prune each other's uploads). An advisory-locked dispatcher (~1 s tick, one lock per kind, continues immediately while a batch is full) claims due items and enqueues them; `BackupTransferConsumers` runs one `Worker` per queue (concurrency 4 backup / 2 restore) and re-reads the row before any I/O. The ledger stays the source of truth: `POST /admin/backups|restores` answers 202 `{runId}`; `GET /admin/backups/runs/:id` reports state/counters/result, and a failed or paused run resumes by starting it again. Each file retries alone (BullMQ: 5 attempts, exponential 1 s; a lost job is re-enqueued from its `queued` row after a 5-min lease); a local ENOSPC/EACCES pauses the whole run. Rows commit at start, so a failed restore is resumable by starting it again with the same manifest (not 409), and permanently missing files leave their assets trashed; backup still writes `manifest.json` last, so a failed run never publishes a manifest over missing bytes. Queue payloads are ids only and are re-read from the DB, so a Redis writer can at most re-trigger an item the run already owns.
- Upload sessions are not a queue: `complete` assembles the parts and reuses `enqueueAssetJobs`, while a 15-min in-process sweeper (advisory-locked, no scheduler dependency) expires stale sessions. If enqueueing fails after the asset rows commit, the session stays `assembled` and a retry re-runs only the enqueues (503 `ENQUEUE_FAILED`; thumb/video/embed/detect reuse jobIds, metadata/faces are idempotent re-enqueues).
- Worker has **no DB access**: every read/write is a core HTTP call via `apps/worker-service/src/core/core-client.service.ts`; bytes go straight to `STORAGE_DIR`. Each call mints a per-job delegated JWT (`WORKER_JWT_SECRET`, `act`) so core scopes by the job's user. Mapping: 400/404/422 → `UnrecoverableError` (no retry); 401/403/429/5xx/timeout → plain error → BullMQ retries (there is no in-process retry loop).
- Payloads zod-validated (`job-schemas.ts`); invalid payloads → `UnrecoverableError`. Processors assert fetched DTOs match the job's ids; core re-enforces ownership via the token.
- Missing models don't fail jobs: the worker warns, patches a `failed` status where a column exists, and completes (a retry would not help); detect has no status column (logs only).
- Redis trust model: the worker mints a JWT for whatever `userId` a payload implies, so a compromised Redis lets an attacker act as any user over core's HTTP API — now including a full account wipe via the `user-delete` consumer and `POST /worker/users/:id/purge/step|finish` (never as admin; those routes' job binding pins the target to the job's own `sub`, but a Redis writer can enqueue that job for anyone) — same blast radius as the old direct-Postgres access, where it could already delete rows.
- Video: h264+aac → skip & mark `ready`. Else one SVT-AV1 pass (`libsvtav1 -preset 8 -crf 32`, `libopus 96k` only with an audio track, downscale only >720p, encode capped at 60 fps) → webm registered through core as a separate `FileRecord` (`purpose: 'transcode'`); originals immutable. Caps: 4h / 7680px / 1h ffmpeg; `transcodeStatus` stays `pending` if the worker dies mid-job.
- Faces: SCRFD-10G is the only detector (`det_10g.onnx`, top-left black-pad 640 letterbox); detection on an EXIF-oriented ≤2048px copy, faces `<40px` skipped; ArcFace `w600k_r50.onnx` **512-dim** embeddings. Detection/embedding/DBSCAN (`eps=0.35`, `minPts=2`, noise reassign `0.30`, centroid `0.30` + `0.05` runner-up margin, O(n²)) stay in the worker; results go through core. No detector provenance anywhere (no job field, setting, or column); `GET api/v1/admin/face-detection` is read-only `{modelAvailable}`. Admin: `POST api/v1/admin/faces/reprocess` (re-detect + re-embed), `POST api/v1/admin/faces/recluster`.
- Other pipelines: detect (YOLO26n 640, conf 0.4, top-200, replace-set), embed (SigLIP2 int8, ≤2048px, 768-dim). All models live under `STORAGE_DIR/models`, provisioned by `pnpm --filter @photox/worker-service <face|vision|detect>-model` (skip-if-present; root postinstall runs all three), never committed; inference loads only from disk (`allowRemoteModels=false`).

## DB / storage

- Single hardcoded `photox` DB; only core connects. TypeORM 1.x: `invalidWhereValuesBehavior` defaults to `throw`, so a possibly-undefined value in a `where` (or in `findOwnedOr404`) is a 500, not a dropped predicate — pin `{ null: 'ignore', undefined: 'ignore' }` on the `DataSource` only if a query legitimately needs the old 0.3 semantics. `select`/`relations` take the object form (`{ id: true }`), never the removed string-array form. `DatabaseModule.forRoot()`: `synchronize: NODE_ENV !== 'production'`, `migrationsRun` in production over `apps/core/src/database/migrations` (Baseline, FileChecksumUnique, UploadSessions, BackupMerges, DropAssetOcr, DropUploadSessionMimeHint, RefreshTokenSessions, AlbumHiddenFromTimeline, BackupTransferRuns, UserDeletes, BackupRunActiveUnique, AlbumAssetsPagingIndex, PersonsFaceCountIndex, StructuralIndexes); **new entity columns need a migration for prod**, and a synchronize-era dev DB must be manually marked migrated before later ones apply. `retryAttempts: 3`, `retryDelay: 3000`, `connectTimeoutMS: 3000` — don't zero them. Resumable-upload state is `upload_sessions` + `upload_session_parts`.
- Boot bootstrap SQL (pgvector ext, `assets_layout_idx`, the versioned `asset_embeddings_hnsw_v1` halfvec index — `CREATE INDEX IF NOT EXISTS`, so a boot never rebuilds it; bump the name's version to change the definition, cube/earthdistance + places GiST) is warn-only per group — core boots degraded rather than failing; search and place resolution fail at query time.
- `LocalStorageService`: files at `STORAGE_DIR/<storageKey>`, atomic save via tmp+rename (EXDEV-safe copy fallback). E2e shares one `storage-data` volume. `sweepUserStorage` (same package) deletes a user's four prefixes by streaming directories, retries each key and reports `{deleted, failed, firstError}`; it never `rm -rf`s a prefix that still has survivors. `STORAGE_DIR/backup-runs/<runId>/` holds backup/restore manifest drafts, temp downloads and the run's work files; the ledger (not the orphan sweep) owns it.
- `HealthService` (core) uses `DataSource.query('SELECT 1')` + a Redis ping, not `@InjectRepository()`; the ping reuses `BullMqService`'s global redis client (no second connection); worker health probes Redis only.

## Web

- Explicit lazy routes in `src/App.tsx` (react-router-dom 7 `useRoutes`); zustand stores; axios client is cookie-only (`withCredentials`, no Bearer header) with proactive-refresh + 401-retry interceptors. Vite proxies `/api`, `/worker`, `/health` to `VITE_API_URL || http://localhost:3000`; `/worker` is e2e plumbing only.
- Dark by default (`<html class="dark">`). Tailwind v4 CSS config (`@import "tailwindcss"` + `@theme` in `app.css`) — no `tailwind.config.*`. Icons: `react-icons/fa6` only.
- Media loads through direct stream URLs (`/api/v1/files/:id/stream`, `/api/v1/faces/:id/thumb`) authenticated by the HttpOnly cookie — blob fetching only for the explicit download action.
- Timeline layout: `useTimelineLayout` fetches the month index, diffs it against the IndexedDB window cache (`src/lib/layoutCache.ts`, user- and filter-namespaced, memory fallback) and fetches only windows whose `version` moved. Cold load still fetches every window — the error-free scroll track needs each window's exact aspect data. `personId` views are memory-only (no fingerprint for clustering).

## Style

- Prettier: semicolons, single quotes, trailing commas, 100-col, 2-space. Strict TS (`noUncheckedIndexedAccess`, `noUnusedLocals`, `noUnusedParameters`). ESLint 10 flat config (`eslint.config.mjs` at the root, type-aware via `projectService: true`) — don't add files it can't typecheck without extending that config's ignores. TS 6 defaults `types` to `[]` and `rootDir` to the tsconfig's directory: every package must list its `types` explicitly (`["node"]`), and core's `tsconfig.json` widens `rootDir` to the workspace because integration specs import worker sources (`tsconfig.build.json` keeps `rootDir: src` for `nest build`).
- `typescript` + `@types/node` pinned versions in devDeps — never `workspace:*`. Workspace deps use `workspace:*`.
- Deliberate simplifications are marked `ponytail:` with ceiling + upgrade path — keep the convention, don't "clean them up".

## Tests / CI

- Vitest 5 (`globals: true`); turbo runs each package's `test`. Single spec: `pnpm --filter @photox/core test src/path.spec.ts` (vitest forwards path filters). Core has two projects: unit `src/**/*.spec.ts` (5s) and integration `test/integration/**/*.spec.ts` (30s tests / 60s hooks, `retry: 1`).
- Core integration runs against **two Testcontainers containers** (`redis:7-alpine` + `pgvector/pgvector:0.8.7-pg16`) owned by `apps/core/test/global-setup.ts`; the worker's run owns one Redis (`apps/worker-service/test/global-setup.ts`). `test-setup.ts` must be imported by helpers (no `setupFiles`). Isolation lives _inside_ the containers: each spec file clones `photox_tmpl` into `photox_t_s<n>` and claims Redis logical DB `<n>` via an `O_EXCL` claim (≤200 slots, container runs `--databases 256`). The template carries vector/cube/earthdistance **and the schema**, baked at run start from `test/integration/entities.ts` — spec apps run `synchronize: false`, so a new entity goes in that list (one shared superset), never in a per-spec array. Containers are labelled `photox.test=*` and are session-owned, never reused: the returned teardown stops them on success and Ryuk reaps them if the run is killed (hence `TESTCONTAINERS_RYUK_PRIVILEGED=true` on Podman), so no container outlives a run. Docker required. Worker integration is Redis-only with a fake `CoreClient`; web tests are colocated jsdom specs (config inline in `vite.config.ts`; `test:browser` is opt-in and not in `verify`); `shared-config`'s `vitest.config.ts` pins its specs to `src/**/*.spec.ts` because the default glob also sweeps the CommonJS `dist/*.spec.js` a build leaves behind (vitest 5 refuses to load itself via `require`).
- Podman/macOS: `TESTCONTAINERS_RYUK_PRIVILEGED=true pnpm verify` (the SELinux VM kills unprivileged Ryuk on socket bind). If you set `DOCKER_HOST=unix://$HOME/.local/share/containers/podman/machine/podman.sock`, also set `TESTCONTAINERS_DOCKER_SOCKET_OVERRIDE=/var/run/docker.sock`; `TESTCONTAINERS_RYUK_DISABLED=true` opts out. These vars pass through turbo.
- No coverage script. Web→core contract = `shared-types` (compile time) + e2e (runtime); deleted pact specs stay deleted.
- e2e (`pnpm test:e2e` = `e2e/run.sh`) runs a compose stack + playwright-bdd: the `setup` project (`04-faces/**` + `05-semantic/semantic-upload.feature`) runs first, serial; `suite` is parallel and takes `--workers=N`. Flags: `E2E_BUILD=1` (rebuild images), `E2E_KEEP=1`, `E2E_PROJECT`, `E2E_WEB_PORT`. Fixed creds `admin@photox.test`/`password123`. Concurrent runs get their own stack/port but share `e2e/.features-gen`, `test-results`, `playwright-report`.
- Jenkins (k8s pod): install `--frozen-lockfile` → Validate in parallel (typecheck / lint / `pnpm test`, dind pre-pulls `pgvector/pgvector:0.8.7-pg16` + `redis:7-alpine`) → `pnpm build`. No e2e stage.
- Mobile is its own gate (`pnpm mobile:verify`), never in turbo, `pnpm verify` or Jenkins. `pnpm mobile:e2e` (`e2e/mobile/run.sh`) is opt-in and also outside every gate: it boots the compose stack plus an Android AVD on the host and is the only mobile coverage of the foreground pipeline (auth, dedup, multipart and session upload, resume across a restart, revoked tokens); real background execution stays unverified without a phone.
